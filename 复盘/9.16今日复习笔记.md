# 一、索引是什么？

一句话：

> **索引是帮助 MySQL 快速查找数据的数据结构。**

例如：

```
SELECT * FROM user WHERE name = '王五';
```

如果 `name` 没有合适的索引，MySQL 可能需要：

```
第1条
 ↓
第2条
 ↓
第3条
 ↓
……
 ↓
大量数据
```

这就是：

> **全表扫描**

建立索引后，MySQL 可以利用索引结构快速定位数据，从而减少需要检查的数据。

# 二、创建索引

今天实际创建了：

```
CREATE INDEX idx_user_name ON user(name);
```

意思：

```
idx_user_name
    ↓
给 user 表的 name 字段创建索引
```

可以通过：

```
SHOW INDEX FROM user;
```

查看索引。

今天看到：

```
Index_type
BTREE
```

# 三、索引不是越多越好

索引可以提高查询效率。

但是索引太多也有成本。

因为：

```
INSERT
UPDATE
DELETE
    ↓
也需要维护索引
```

所以：

> **索引不是越多越好，而是应该根据实际查询场景合理建立。**

# 四、EXPLAIN 是干什么的？

可以使用：

```
EXPLAIN SELECT * FROM user WHERE name = '王五';
```

分析一条 SQL 的执行情况。

今天重点认识了几个字段。

## 1. possible_keys

表示：

> **这条 SQL 可能使用哪些索引。**

例如：

```
possible_keys
idx_user_name
```

说明：

```
MySQL 发现 idx_user_name 这个索引可以用于这条查询
```

## 2. key

这个非常重要。

表示：

> **MySQL 最终实际选择使用的索引。**

例如：

```
key
idx_user_name
```

说明：

> 这次查询实际使用了 `idx_user_name`。

如果：

```
key
NULL
```

说明：

> 这次查询没有使用索引。

# 五、今天做的第一个实验

执行：

```
CREATE INDEX idx_user_name ON user(name);
```

然后：

```
EXPLAIN SELECT * FROM user WHERE name = '王五';
```

结果关键部分：

```
possible_keys   idx_user_name
key             idx_user_name
```

说明：

> MySQL 使用了 `idx_user_name` 索引。

# 六、没有索引的字段

我们又测试：

```
EXPLAIN SELECT * FROM user WHERE age = 18;
```

因为：

```
name
 ↓
有索引

age
 ↓
没有索引
```

所以结果：

```
possible_keys   NULL
key             NULL
```

说明：

> 这次查询没有可以利用的索引，也没有实际使用索引。

# 七、B+Tree 是什么？

今天看到：

```
Index_type = BTREE
```

MySQL InnoDB 的普通索引主要使用：

> **B+Tree**

暂时可以简单理解：

> **B+Tree 是一种多路平衡树，可以把大量索引数据组织成有层次的结构，从而帮助 MySQL 更快地定位数据。**

简单理解：

```
大量数据
    ↓
B+Tree 索引
    ↓
快速缩小查找范围
    ↓
定位数据
```

# 八、为什么 B+Tree 适合数据库索引？

B+Tree 是一种：

```
多路
+
平衡
+
树形结构
```

一个节点可以保存多个值：

```
       [20 | 40 | 60 | 80]
      /    |    |    |    \
```

相比普通二叉树，它可以让树的高度比较低。

树的高度较低意味着：

```
需要经过的层数少
        ↓
减少磁盘 I/O
        ↓
提高查询效率
```

面试可以先记：

> **B+Tree 是一种多路平衡树，树高较低，适合数据库索引，可以减少磁盘 I/O，提高查询效率。**

# 九、LIKE 和索引

这是今天非常重要的一个知识点。

我们已经有：

```
CREATE INDEX idx_user_name ON user(name);
```

## 1. LIKE '%王%'

执行：

```
EXPLAIN SELECT * FROM user WHERE name LIKE '%王%';
```

结果：

```
possible_keys   NULL
key             NULL
```

说明：

> 这次没有使用 `idx_user_name`。

原因：

```
LIKE '%王%'
```

前面有 `%`。

MySQL 不知道应该从索引的哪个位置开始有效定位。

因此普通 B+Tree 索引通常无法有效利用。

# 十、LIKE '王%'

再执行：

```
EXPLAIN SELECT * FROM user WHERE name LIKE '王%';
```

结果：

```
type            range
possible_keys   idx_user_name
key             idx_user_name
```

说明：

> **这次 MySQL 使用了** `**idx_user_name**`**。**

因为：

```
LIKE '王%'
```

是从左边开始匹配。

MySQL 可以利用索引有序的特点进行范围查找。

# 十一、最重要的 LIKE 对比

| SQL                | 普通 B+Tree 索引   |
| ------------------ | ------------------ |
| `name = '王五'`    | ✅ 可以使用         |
| `name LIKE '王%'`  | ✅ 可以使用         |
| `name LIKE '%王%'` | ❌ 通常无法有效使用 |

核心区别：

```
'王%'
 ↑
从左边开始
```

而：

```
'%王%'
 ↑
前面不知道从哪里开始
```

# 十二、和 MyBatis-Plus 的联系

之前学习过：

```
wrapper.like("name", "王");
```

对应：

```
name LIKE '%王%'
```

这种查询通常无法有效利用普通 B+Tree 索引。

而：

```
wrapper.likeRight("name", "王");
```

对应：

```
name LIKE '王%'
```

这种查询可以利用普通索引进行范围查找。

所以以后看到：

```
wrapper.like()
```

不要简单认为：

> “一定走索引。”

应该先看它最终生成的 SQL。

# 十三、今天的 EXPLAIN 重点

# 十五、今天的面试题

## 题目 1：什么是索引？

答案：

> 索引是帮助 MySQL 快速查找数据的数据结构，可以减少全表扫描，提高查询效率。

## 题目 2：怎么查看一条 SQL 有没有使用索引？

答案：

> 可以使用 `EXPLAIN` 分析 SQL，重点查看 `key` 字段。`key` 显示实际使用的索引，如果是 `NULL`，说明没有使用索引。

## 题目 3：`possible_keys` 和 `key` 有什么区别？

答案：

```
possible_keys
↓
可能使用哪些索引

key
↓
最终实际使用哪个索引
```

## 题目 4：MySQL 为什么使用 B+Tree？

答案：

> B+Tree 是一种多路平衡树，树的高度比较低，可以减少磁盘 I/O，帮助 MySQL 快速定位数据。

## 题目 5：为什么 `LIKE '%王%'` 通常不能有效使用普通 B+Tree 索引？

答案：

> 因为前面有 `%`，无法根据索引的最左侧值进行有效定位，因此普通 B+Tree 索引通常无法有效利用。

## 题目 6：`LIKE '王%'` 能不能使用索引？

答案：

> 可以利用普通 B+Tree 索引进行范围查找，因为匹配条件是从左边开始的。

# 十六、今天最应该记住的 5 句话

```
1. 索引是帮助 MySQL 快速查找数据的数据结构。

2. EXPLAIN 可以用来分析 SQL 的执行情况。

3. key 可以用来判断实际使用了哪个索引。

4. MySQL InnoDB 的普通索引主要使用 B+Tree。

5. LIKE '%关键词%' 通常无法有效利用普通 B+Tree 索引，
   LIKE '关键词%' 可以利用索引进行范围查找。
```

# 十七、下一步学习

> **联合索引 + 最左匹配原则**

例如：

```

```

然后研究：

```
WHERE name = '王五'

```

为什么有的能利用索引，有的不能。

这个是 **MySQL 面试非常常见的知识点**。
