# 一、参数校验

## 1. 为什么需要参数校验？

前端传过来的数据不一定正确。

例如注册：

```
{
    "username": "",
    "password": "123"
}
```

这种数据就应该被后端拦截。

所以我们使用：

```
@Valid
```

开启参数校验。

# 二、常用校验注解

今天学习了：

```
@NotBlank
```

表示：

> 字符串不能为空，也不能是空白。

例如：

```
@NotBlank
private String username;
@Size(min = 6)
```

表示：

> 字符串长度至少为 6。

例如：

```
@Size(min = 6, message = "密码长度不能少于6位")
private String password;
```

# 三、@RequestBody + @Valid

注册接口：

```
@PostMapping("/test/register")
public String register(
        @Valid @RequestBody RegisterRequest request) {

    return "注册成功";
}
```

这里有两个重点：

### @RequestBody

负责：

```
JSON
 ↓
Java对象
```

例如：

```
{
    "username": "张三",
    "password": "123456"
}
```

转换成：

```
RegisterRequest
```

### @Valid

负责：

> 开启参数校验。

所以：

```
@Valid @RequestBody RegisterRequest request
```

可以理解成：

```
前端 JSON
    ↓
@RequestBody
    ↓
Java对象
    ↓
@Valid
    ↓
检查参数
    ↓
通过 → Controller继续执行
失败 → 抛出异常
```

# 四、全局异常处理

如果每个 Controller 都自己处理异常，会出现大量重复代码。

所以我们创建：

```
@RestControllerAdvice
public class GlobalExceptionHandler {
}
```

它可以理解成：

> **全局异常处理器。**

# 五、@RestControllerAdvice

核心理解：

```
@RestControllerAdvice
```

作用：

> 统一处理 Controller 层产生的异常。

# 六、@ExceptionHandler

例如：

```
@ExceptionHandler(MethodArgumentNotValidException.class)
public Result<Void> handleValidationException(
        MethodArgumentNotValidException e) {

    String message = e.getBindingResult()
            .getFieldError()
            .getDefaultMessage();

    return new Result<>(
            400,
            message,
            null
    );
}
```

这里：

```
@ExceptionHandler(MethodArgumentNotValidException.class)
```

意思：

> 如果出现 `MethodArgumentNotValidException`，就交给这个方法处理。

# 七、参数校验失败的完整流程

例如密码只有：

```
123
```

但是要求至少 6 位。

流程：

```
前端
 ↓
POST /test/register
 ↓
@RequestBody
 ↓
@Valid
 ↓
参数校验失败
 ↓
MethodArgumentNotValidException
 ↓
GlobalExceptionHandler
 ↓
返回统一 Result
```

最后返回：

```
{
    "code": 400,
    "message": "密码长度不能少于6位",
    "data": null
}
```

# 八、Result<T> 统一返回

我们之前创建了：

```
public record Result<T>(
        Integer code,
        String message,
        T data
) {
}
```

作用：

> **让接口返回格式统一。**

例如成功：

```
{
    "code": 200,
    "message": "成功",
    "data": {}
}
```

失败：

```
{
    "code": 400,
    "message": "参数错误",
    "data": null
}
```

所以：

```
Result<T>
```

可以理解成：

```
code
 ↓
状态

message
 ↓
提示信息

data
 ↓
真正的数据
```

# 九、JWT 是什么？

JWT 可以先简单理解成：

> **登录成功之后，后端发给用户的一张“通行证”。**

例如：

```
用户登录
 ↓
用户名 + 密码
 ↓
验证成功
 ↓
生成 JWT
 ↓
返回给前端
```

# 十、JWT 的三个组成部分

JWT：

```
Header.Payload.Signature
```

也就是：

```
Header
Payload
Signature
```

面试记住：

> **JWT = Header + Payload + Signature**

# 十一、Payload 里面可以放什么？

我们今天把：

```
userId
```

放进 JWT。

代码：

```
.subject(String.valueOf(userId))
```

例如：

```
用户ID = 1
```

那么 JWT 中就保存了：

```
sub = 1
```

以后后端解析 JWT，就可以知道：

```
当前用户是谁
```

# 十二、JWT 不是加密

这一点很重要：

> **JWT 的 Payload 默认不是加密的。**

所以不要往 JWT 里面放：

```
密码
银行卡密码
敏感隐私数据
```

JWT 更主要是：

> **携带身份信息 + 防止内容被篡改。**

# 十三、登录接口生成 JWT

我们今天写过：

```
String token = JwtUtil.createToken(1L);
```

意思：

> 根据用户 ID 生成 JWT。

然后返回：

```
return new Result<>(
        200,
        "登录成功",
        new LoginResponse(token)
);
```

返回给前端：

```
{
    "code": 200,
    "message": "登录成功",
    "data": {
        "token": "xxxxx"
    }
}
```

# 十四、前端以后怎么带 JWT？

前端请求接口时：

```
Authorization: Bearer xxxxx
```

其中：

```
Authorization
```

是请求头。

```
Bearer
```

可以先理解成：

> 后面跟着的是 Token。

# 十五、后端怎么拿 Token？

我们之前在 Controller 中写过：

```
@RequestHeader("Authorization") String authorization
```

得到：

```
Bearer xxxxx
```

然后：

```
String token = authorization.substring(7);
```

去掉：

```
Bearer 
```

得到真正的：

```
xxxxx
```

# 十六、JwtUtil

我们创建了：

```
JwtUtil
```

现在不需要背里面所有代码。

只需要知道两个方法：

```
JwtUtil.createToken(userId)
```

作用：

> 生成 JWT。

```
JwtUtil.getUserId(token)
```

作用：

> 验证 JWT，并获取用户 ID。

# 十七、JWT 验证成功

例如：

```
Authorization: Bearer 正确的Token
```

流程：

```
请求
 ↓
获取 Token
 ↓
JwtUtil.getUserId(token)
 ↓
验证成功
 ↓
得到 userId
 ↓
继续执行接口
```

我们之前测试成功得到：

```
当前用户ID：1
```

# 十八、JWT 验证失败

例如前端故意传：

```
Authorization: Bearer abc123
```

这是假的 Token。

执行：

```
JwtUtil.getUserId(token)
```

会产生：

```
JwtException
```

然后交给：

```
@ExceptionHandler(JwtException.class)
```

处理。

最终返回：

```
{
    "code": 401,
    "message": "登录已失效，请重新登录",
    "data": null
}
```

今天我们已经**实际测试成功**。

# 十九、为什么需要 JWT 拦截器？

一开始我们是在 Controller 里面自己检查：

```
@RequestHeader("Authorization")
```

然后：

```
JwtUtil.getUserId(token)
```

但是如果项目有很多接口：

```
用户信息
订单
购物车
地址
收藏
评论
...
```

每个 Controller 都写一遍，非常麻烦。

所以我们引入：

```
JwtInterceptor
```

可以理解成：

> **统一的 JWT 门卫。**

# 二十、JwtInterceptor 做什么？

今天我们已经一步一步写出了：

```
public class JwtInterceptor
        implements HandlerInterceptor {
```

然后实现：

```
@Override
public boolean preHandle(
        HttpServletRequest request,
        HttpServletResponse response,
        Object handler
) throws Exception {
```

`preHandle()` 可以理解成：

> **Controller 执行之前先执行。**

# 二十一、拦截器目前做了什么？

第一步：

```
String authorization =
        request.getHeader("Authorization");
```

意思：

> 从请求头获取 Authorization。

第二步：

```
if (authorization == null) {
    return false;
}
```

意思：

> 没有 Authorization，直接拦截。

第三步：

```
String token = authorization.substring(7);
```

意思：

> 去掉 `Bearer `，得到真正的 JWT。

第四步：

```
String userId = JwtUtil.getUserId(token);
```

意思：

> 验证 JWT，并获取用户 ID。

# 二十二、拦截器的整体流程

现在可以把它理解成：

```
浏览器
   ↓
请求接口
   ↓
JwtInterceptor
   ↓
有没有 Authorization？
   ↓
 ┌──────────────┐
 ↓              ↓
没有            有
 ↓              ↓
拦截            获取 Token
                ↓
          JwtUtil 验证
                ↓
          ┌─────┴─────┐
          ↓           ↓
        正确          错误
          ↓           ↓
        放行          401
          ↓
      Controller
```

# 二十三、WebMvcConfig

我们还创建了：

```
@Configuration
public class WebMvcConfig
        implements WebMvcConfigurer {
}
```

它是：

> **Spring MVC 的配置类。**

然后：

```
@Override
public void addInterceptors(
        InterceptorRegistry registry) {

    registry.addInterceptor(
            new JwtInterceptor()
    );

```

作用：

> **把 JwtInterceptor 注册到 Spring MVC 中。**

可以理解成：

```
JwtInterceptor
      ↓
只是写好了一个“门卫”

WebMvcConfig
      ↓
告诉 Spring
“把这个门卫安排到请求流程里”
```

# 二十四、目前 JWT 还没完全结束

我们现在已经完成：

```
JWT生成
      ↓
JWT返回前端
      ↓
Authorization携带JWT
      ↓
JwtInterceptor
      ↓
JWT验证
```

但是还有一个问题：

```
登录接口
```

用户登录的时候本来就没有 Token。

如果所有接口都经过 JWT 拦截器：

```
POST /test/login
       ↓
JwtInterceptor
       ↓
没有 Token
       ↓
被拦截
```

那就没办法登录了。

所以**下一步要学习的就是：**

```
.excludePathPatterns("/test/login")
```

让登录接口不要经过 JWT 拦截器。

# 二十六、面试题复习

## 题目 1

`@Valid` 是干什么的？

**答案：**

> 开启参数校验。

## 题目 2

`@RestControllerAdvice` 是干什么的？

**答案：**

> 统一处理 Controller 层异常。

## 题目 3

为什么使用 `Result<T>`？

**答案：**

> 让接口返回格式统一，方便前端处理。

## 题目 4

JWT 有哪三个部分？

**答案：**

> Header、Payload、Signature。

## 题目 5

JWT 一般放在哪里？

**答案：**

> HTTP 请求头的 `Authorization` 中。

## 题目 6

JWT 拦截器是干什么的？

**答案：**

> 在 Controller 执行之前统一检查 JWT。

## 题目 7

JWT 验证失败应该返回什么状态？

**答案：**

```
401
```

表示：

> 未认证 / 登录身份无效。

# 今日一句话总结

> **@Valid 负责检查参数，@RestControllerAdvice 负责统一处理异常，Result<T> 负责统一返回格式，JWT 负责登录身份认证，JwtInterceptor 负责在接口执行前统一检查 JWT。**
